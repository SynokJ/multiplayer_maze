# Route one WSS port to many Unity rooms

**Build the game around a server-side host, not a browser host.** A WebGL build cannot accept incoming connections, so "client as host" has to be implemented as either (a) a headless Linux process that runs the host role while every browser is a client, or (b) a dumb relay that forwards messages while one browser holds game-level authority. Unity's own Transport manual says that in WebGL "only WebSocket connections in client mode are supported (it is however still possible to host games if using Unity Relay)" ([Transport 2.5 manual](https://docs.unity3d.com/Packages/com.unity.transport@2.5/manual/)). Unity Relay is capped (free to 50 average monthly CCU, then $0.16 per extra CCU) ([Unity support](https://support.unity.com/hc/en-us/articles/4410136449812-How-is-the-Relay-Service-Priced)), so it fails your "no limitations" rule. The recommended stack is: Unity 6.3 LTS; Netcode for GameObjects (NGO) 2.x with Unity Transport 2.x over WebSockets (or Mirror, or Colyseus if the game logic can live in Node); a Node matchmaker; and one reverse proxy (Caddy or nginx) on port 443 that terminates TLS. The old "one public port per session" workaround is not needed. Keep room servers on plain `ws://127.0.0.1:<port>` and let the proxy or a Node gateway map `/room/<id>` to the right local port, so the browser only ever sees `wss://host/room/<id>`. That routing layer is my design inference, not a documented Unity pattern, and it carries three unverified assumptions, listed below. All evidence comes from web-search summaries, because every direct page fetch failed. Sourced facts are cited, and inference is labeled.

## A WebGL build cannot listen, so "client as host" means a server-side host

Browsers expose no listening sockets. The Unity Transport documentation, as relayed by search summaries, says starting a server inside a WebGL player is impossible even over WebSockets ([Unity forum](https://discussions.unity.com/t/netcode-webgl-build-cant-connect-to-server-or-host/874990), [Transport WebSockets manual](https://docs.unity3d.com/Packages/com.unity.transport@2.5/manual/websockets.html)). The Transport 2.0 announcement confirms the shape: the WebSocket implementation runs as client or server on every platform, but on WebGL as client only ([announcement](https://discussions.unity.com/t/unity-transport-is-now-available-as-a-2-0-pre-release-version-package/912509/1)). An open NGO issue reports a WebGL session host that listens while peers cannot connect, so do not plan around it ([NGO #4111](https://github.com/Unity-Technologies/com.unity.netcode.gameobjects/issues/4111)). Its status was not verified. The Transport WebSocket support also only connects Transport clients to Transport servers. It is not a general WebSocket library, so a Node relay cannot simply talk to an NGO client ([manual](https://docs.unity3d.com/Packages/com.unity.transport@2.5/manual/websockets.html)).

That leaves two workable models for requirement (3), "host may be a client or a dedicated server":

| Model | How it works | Fit |
|---|---|---|
| Headless host | A Linux Dedicated Server build, or a headless build that runs NGO/Mirror as Host, owns the simulation. The first joiner gets "room owner" privileges at the game level. | Best fit for NGO or Mirror. Mirror's SimpleWebTransport is WebSocket-based and designed for WebGL, and a forum report describes a headless Linux Mirror host serving WebGL clients, though the author called it unfinished ([Unity forum](https://discussions.unity.com/t/engine-for-browser-multiplayer-game-using-webgl/816327), [SimpleWebTransport](https://github.com/MirrorNetworking/SimpleWebTransport)). |
| Relay with a logical host | One browser owns the game rules and sends messages through a Node `ws` or Colyseus relay. | Feels like player-hosting but is a custom message layer. NGO and Mirror would need a custom transport. Inference only. |

True browser-to-browser hosting would need WebRTC, which is weak in the mainstream Unity stacks. Mirror's WebRTC transport is reported as experimental and desktop-only, with no relay fallback, and a proof of concept in a full mesh "probably won't scale past like 10 people" ([Unity forum](https://discussions.unity.com/t/multiplayer-in-browser-games/925522), [musv2022](https://github.com/hiinaspace/musv2022)). Normcore is WebRTC-based but has a 30 CCU cap, and its WebGL support is alpha ([Normcore pricing](https://normcore.io/pricing), [docs](https://docs.normcore.io/platforms/webgl)). I'd skip WebRTC. As a design rule, treat the host as a server role. If a player is "host", give that player only lobby privileges such as start, kick and settings, and keep authority on the server. That also removes host migration, for which no WebGL-specific source was found.

## Only self-hosted open-source stacks stay free without caps

For requirement (4), the sourced picture is clear. Photon has a 20 CCU free tier, and its 100 CCU plan is reported by Photon staff as a one-time 12-month subscription ([Photon pricing](https://doc.photonengine.com/zh-cn/photon/current/pricing), [Photon forum](https://forum.photonengine.com/discussion/20628/how-to-publish-a-multiplayer-game-on-steam-cost-effective)). Unity Relay has the 50 CCU cap above, with bandwidth capped at 150 GiB per month free. Normcore has the 30 CCU, 10-room, one-hour-session cap above. All three are hosted-only. The uncapped options are NGO with Transport on your own server, Mirror with SimpleWebTransport, FishNet with Bayou, Colyseus (MIT), and Nakama. FishNet's Bayou is a repurposed SimpleWebTransport with an "Enable WSS" setting ([Bayou docs](https://fish-networking.gitbook.io/docs/manual/components/transports/bayou)). Your only cost is the server and the TLS endpoint.

Unity Personal is free up to US$200,000 trailing-12-month revenue or funding, and the splash screen is optional with Unity 6 ([Unity pricing updates](https://unity.com/pricing-updates)). That is a revenue cap, so strictly it is a restriction on requirement (4), but it is a ceiling, not a technical limit. Unity 6.3 LTS is supported until December 2027, while 6.0 LTS support ends October 2026 ([Unity 6 support](https://unity.com/releases/unity-6/support)). NGO needs 1.2.0+ and Transport 2.0.0+ for WebGL, and NGO 2.x pairs with Transport 2.x on Unity 6 ([NGO 2.8 manual](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.8/manual/index.html)). Exact current patch versions were not found, so pin them in `Packages/packages-lock.json`.

The Linux server build uses `-buildTarget Linux64 -standaloneBuildSubtarget Server`, and Unity defines `UNITY_SERVER` for it ([Unity 6.2 manual](https://docs.unity3d.com/6000.2/Documentation/Manual/dedicated-server-build.html)). I found no licensing restriction on building it under Personal, but that is unconfirmed. The choice between Unity-side and Node-side authority drives everything else. Colyseus runs many rooms in one Node process, with `Create` and `JoinOrCreate` matchmaking calls and automatic state patches ([Colyseus Unity SDK](https://docs.colyseus.io/getting-started/unity-sdk)), but you give up Unity-side simulation. A maze game with simple movement and state sync may fit, which is why I'd prototype it first. Check the Colyseus Unity SDK against the server version before committing, because the 0.17 docs reportedly list only the TypeScript SDK ([same source](https://docs.colyseus.io/getting-started/unity-sdk)). WebGL support in the SDK was not confirmed.

## One WSS port works if the proxy or Node maps room paths to local ports

The old workaround of one free port per session existed because each Unity server process wanted its own TLS-capable public port. The fix is to stop exposing game ports. The sourced facts are: nginx proxies WebSockets with path-based `location` blocks, but must forward `Upgrade` and `Connection` with `proxy_http_version 1.1` ([OneUptime](https://oneuptime.com/blog/post/2026-01-24-websocket-nginx-reverse-proxy/markdown), [GetPageSpeed](https://www.getpagespeed.com/server-setup/nginx/nginx-websocket-proxy)). Caddy's `reverse_proxy` usually handles WebSockets without extra config ([Caddy community](https://caddy.community/t/how-to-use-self-signed-cert-with-reverse-proxy/25438)). Colyseus can also split a standalone matchmaker from separate game servers, but each game server then needs its own public address and a shared presence layer such as Redis ([Colyseus docs](https://docs.colyseus.io/matchmaker/standalone)). That is the same multi-address problem, so it is no help here.

My recommended design is inference, not a documented pattern. The Node lobby (REST plus WebSocket) listens on 127.0.0.1. For each new room it picks a port from an internal range, for example 7800-7899, and spawns a Unity Linux server bound to `ws://127.0.0.1:<port>`. The proxy terminates TLS on 443. Because nginx locations are static, dynamic routing has two options. In the first, Node acts as the WebSocket gateway: it reads the `/room/<id>` path and pipes the upgraded socket to the room's port. In the second, the proxy does a lookup per request, for example nginx `map` or `auth_request`, or Caddy's Admin API. Gateway piping is the simpler of the two. Add an explicit ceiling on concurrent rooms, because per-instance RAM for a headless Unity process was not measured in any source and should be tested on the VM.

Three assumptions in this design are unverified and are the first things to test:

- **Path support in the transport.** Path-prefix routing needs the Unity transport to accept a path in the WebSocket URL. Check the field in the exact Transport version you install.
- **Piping through Node.** Frames should pass through unchanged, but nobody in the notes tested a Node gateway in front of a Unity WebSocket server.
- **Proxy idle timeouts.** nginx closes idle proxied connections after 60 s by default. The remedy is a raised `proxy_read_timeout` or 30-60 s application pings ([websocket.org](https://websocket.org/guides/infrastructure/nginx/)). No source confirms that ping frames reset nginx's timer in every setup, so test it.

Per-session ports are workable on a LAN but weaker everywhere else. Each public port needs a firewall rule, a VirtualBox forward rule, and TLS, and restrictive networks often permit only 80 and 443. That last point is reasoning, not sourced. Process management is also unsourced engineering guidance. Spawn with `-batchmode -nographics -port P -logFile -`, keep a registry of room, port, pid and state, wait for a ready signal before returning the room URL, and kill rooms that are empty beyond a grace period or have stopped sending heartbeats. Free ports on the `exit` event, kill orphans at lobby start, and run the lobby under systemd. Agones and Open Match target Kubernetes and are overkill for one VM; that judgment is also unsourced.

## WSS fails on certificate trust, not on code

An HTTPS page that opens `ws://` gets a Mixed Content error and a SecurityError, and the fix is `wss://` ([Tencent Cloud Q&A](https://developer.cloud.tencent.com/ask/sof/101081573), [Unity Transport manual](https://docs.unity3d.com/Packages/com.unity.transport@2.5/manual/websockets.html)). Let's Encrypt documents that loopback addresses count as "potentially trustworthy", but that HTTPS pages still cannot call non-secure URLs ([Let's Encrypt](https://letsencrypt.org/tr/docs/certificates-for-localhost/)). I found no loopback or LAN-IP exemption for Chrome or Safari, and Chrome's separate Local Network Access permission layer can add prompts for private targets ([localtonet](https://localtonet.com/blog/chrome-local-network-access-apis-websockets), a third-party guide). If the page itself is plain `http://`, `ws://` is not mixed content. That is standard browser behavior, but no fetched source here confirmed it. So the cheapest dev loop is an http page plus `ws://` on the LAN with no certificates, with a caveat: plain HTTP is not a secure context, so test any feature that needs one.

Terminate TLS at the proxy rather than in the game process. Unity Transport can do WSS itself, using `WithSecureServerParameters(certificate, privateKey)` on the server and `WithSecureClientParameters(serverName)` on the client, but the docs state that self-signed certificates do not work in browsers by default ([manual](https://docs.unity3d.com/Packages/com.unity.transport@2.5/manual/websockets.html)). In an NGO 2.2 / Transport 2.4 thread, ticking "Use Encryption" was not enough, and Unity staff suggested a TLS-terminating reverse proxy ([Unity Discussions](https://discussions.unity.com/t/issues-setting-up-encrypted-websocket-connection-with-unity-transport/1620104)). Mirror's own SSL settings are marked obsolete in favor of a reverse proxy ([Mirror docs](https://mirror-networking.gitbook.io/docs/manual/transports/websockets-transport)). That makes the proxy the reliable choice, and it keeps certificate renewal out of the game.

For certificates, the sourced options are:

- **Let's Encrypt IP certificates.** Generally available since 15 January 2026, free, with a 160-hour lifetime, for public IPs only ([Linuxiac](https://linuxiac.com/lets-encrypt-launches-ip-address-certificates-with-6-day-lifetimes/), [Stackscale](https://www.stackscale.com/blog/lets-encrypt-opens-the-door-to-https-by-ip/)). They need an auto-renewing ACME client. Caddy support and the validation methods for IP certificates were not verified.
- **DuckDNS plus Caddy DNS-01.** Works with the `caddy-dns/duckdns` module and reportedly works even when the A record points to a LAN IP ([caddy-dns/duckdns](https://github.com/caddy-dns/duckdns), [Caddy community](https://caddy.community/t/dns-challenge-with-duckdns/14994)). This is the one sourced route to a browser-trusted certificate for a VM that is not publicly reachable.
- **Caddy `tls internal`.** Issues certificates from a local CA, and the root must be installed on every client ([Caddy community](https://caddy.community/t/how-to-use-self-signed-cert-with-reverse-proxy/25438)). It is fine for your own machines, but not for outside testers. One user hit a 502 combining an IP site with an HTTPS upstream, which shows another edge case ([Caddy community](https://caddy.community/t/v2-reverse-proxy-with-self-signed-node-fails-on-ip/8330)).
- **To avoid:** sslip.io, where users hit Let's Encrypt rate-limit errors on the shared domain ([OpenVidu thread](https://openvidu.discourse.group/t/deployment-without-domain/5474)). Cloudflare Quick Tunnels have a 200 in-flight request limit and no SLA ([Cloudflare](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)). ngrok's free plan caps data at 1 GB per month ([ngrok](https://ngrok.com/docs/pricing-limits/free-plan-limits)), and its docs contradict each other on endpoint counts, so confirm on the live page. Tailscale Funnel offers a stable `ts.net` HTTPS name on ports 443, 8443 and 10000, with unpublished bandwidth limits ([Tailscale](https://tailscale.com/kb/1223/funnel)). WebSocket support through Funnel and Quick Tunnels is unconfirmed.

mkcert is a plausible local CA for the dev machine, but the notes did not verify its documentation, so treat that as inference.

## The VirtualBox VM is a faithful test server if you mirror production

For requirement (5), VirtualBox networking has three modes. Bridged gives the VM its own LAN IP, reachable without port forwarding, at the cost of exposure ([Cleverence](https://www.cleverence.com/articles/oracle-documentation/6-5-bridged-networking-oracle-vm-virtualbox-3742/)). NAT blocks inbound traffic unless you add per-port forward rules, and peers then connect through the host IP ([DevGenius](https://blog.devgenius.io/choosing-the-right-virtualbox-network-adapter-nat-host-only-or-bridged-188003a260de)). Host-only reaches only the host and other VMs. Bridged is simplest for phones and other devices, though Wi-Fi bridging can be flaky (my inference). With NAT, forward only 80 and 443, and open the host firewall. A NAT or LAN VM is not publicly reachable, so Let's Encrypt IP certificates and DuckDNS HTTP-01 will not work, and DuckDNS DNS-01 or a local CA is the way in. The rest of the VM recipe is general practice, not sourced: Ubuntu Server LTS with Caddy or nginx, Node LTS, ufw allowing only 22, 80 and 443, and systemd units for the matchmaker and the dedicated-server launcher. Deploy with `rsync` over SSH rather than shared folders.

Serve the WebGL files and the API from the same proxy origin, with `/` static, `/api/` and `/room/` proxied. That removes CORS, which is a real WebGL trap: cross-origin `UnityWebRequest` needs server CORS including a correct OPTIONS preflight, and a 400 or 403 on OPTIONS breaks requests that work in the Editor ([Unity docs](https://docs.unity3d.com/ja//Manual/webgl-networking.html), [itch.io thread](https://itch.io/t/367395/unity-webgl-and-cors)). For the build itself, pre-compressed files need matching headers: `.br` needs `Content-Encoding: br`, and `.wasm` needs `application/wasm` ([Unity nginx config](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/webgl/building-distribution/server-configuration-code-samples/web-server-config-nginx)). If you cannot control headers, Decompression Fallback exists but enlarges the loader and slows loading ([Unity deploying docs](https://docs.unity3d.com/2020.3/Documentation/Manual/webgl-deploying.html)). Each production host differs here. itch.io reports on Brotli conflict, so gzip is safer there ([itch.io thread](https://itch.io/t/1909856/brotli-support-for-unity-webgl-builds)). That is a user claim, not official guidance.

Oracle Always Free is the only free target in the notes that can run both the files and the server: 4 Ampere A1 OCPUs and 24 GB RAM, with idle instances reclaimable if 95th-percentile CPU, network and memory all stay under 20% for 7 days ([Oracle](https://docs.oracle.com/en-us/iaas/Content/FreeTier/resourceref.htm)). Capacity availability, egress allowance and card verification were not verified. Static hosts (GitHub Pages, itch.io, Cloudflare Pages) can only serve the build, and since they are HTTPS, they force a trusted `wss://` endpoint. Their header behavior was not confirmed. If the VM mirrors that production shape (same proxy, same path routing, same TLS method), development and deployment diverge less.

## Hidden pitfalls cluster around browser throttling, tooling gaps and unverified claims

The best-documented runtime hazard is background tabs. Browsers update hidden tabs about once per second, and `Time.time` runs slower even with `Application.runInBackground` on ([Unity WebGL performance](https://docs.unity3d.com/6000.2/Documentation/Manual/webgl-performance.html)). One report says a Photon WebSocket disconnected on tab switch ([Unity forum](https://forum.unity.com/threads/webgl-issues.319584/)), and a vendor blog advises reconnecting on visibility change and requesting a full state resync ([bugnet](https://bugnet.io/blog/how-to-fix-unity-webgl-game-frozen-after-tab-throttling-in-background)). Whether a WebSocket stays alive in a throttled tab was not found. Design the server to tolerate roughly a one-second silence, drive ticks on the server rather than the client frame rate, and support a rejoin token with a 30-60 second window (inference). This also constrains testing. Multiplayer Play Mode runs up to four local Editor players ([MPPM docs](https://mp-docs.dl.it.unity3d.com/mppm/current/about/)), so it tests netcode but not real WebGL behavior. Use separate, visible browser windows for final checks. Headless Node bots can fill rooms (inference).

On build tooling, the Linux server build and the WebGL build can both run locally in batchmode from an editor script, which is the simplest free pipeline (inference). GameCI with Personal licenses is fragile: the old alf-to-ulf flow no longer works, the manual `.ulf` stored as a secret reportedly expires, and a pasted-`.ulf` workaround rests on one unverified user report ([GameCI #408](https://github.com/game-ci/documentation/issues/408), [unity-license-activate](https://github.com/game-ci/unity-license-activate)). GitHub private-repo minute quotas were only confirmed from third-party material ([GitHub docs](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). React is optional. react-unity-webgl must match the Unity version, and Unity 6.3 support was not confirmed ([installation](https://react-unity-webgl.dev/docs/getting-started/installation)). For a prototype, plain HTML plus Unity UI is likely faster (inference). Generic WebGL cautions, all unsourced and worth verifying: no raw TCP/UDP or threads, so only WebSocket or WebRTC transports work; stripping can remove reflection-used types; browsers cache old builds, so hash filenames; and Linux server binaries need `chmod +x`.

## Conclusion

The central finding is that the "one port per session" problem was never about WebSocket capacity. It came from letting game servers face the internet. Once the browser sees only `wss://host/room/<id>` and rooms sit on localhost, TLS, firewall and VirtualBox rules collapse to one port. Likewise, "client as host" is best read as an authority question, not a networking one: a server process owns the simulation, and the "host" player holds lobby privileges.

The evidence is thinner than the design is confident. No source verifies path-routed Unity WebSocket servers behind Caddy or nginx, headless Unity memory per room, or whether idle pings keep proxied sockets alive. The cheapest next step is a spike on the VM: one Unity Linux server, one Node gateway, Caddy with DuckDNS DNS-01, two visible browser windows. If the transport rejects a URL path, or per-room RAM is too high, fall back to Colyseus rooms in one process, or Mirror with SimpleWebTransport. Both stay free and uncapped.
